# M2.9 Design — Baseline ↔ Challenger Pair Run-Once Operation

> **Status:** design / planning only (no code). Produced during a guarded session at HEAD `0452a84`.
> **Scope boundary:** designs *how* a user safely accumulates SignalLogs for a baseline+challenger **pair**
> under one human-triggered action. Implements nothing — no pair endpoint, no run, no SignalLog, no
> scheduler change, no order/trade, no migration.

## 0. Context

Completed: AI analysis → PENDING proposal → DRAFT challenger version → prepared → active session →
read-only comparison (M2.1/M2.6) → **selected-session run-once (M2.8)** → SignalLog reflected in M2.1.
M2.8 evaluates **one** session once via `PaperSignalSessionRunOnceService.run_once(session_id, confirmed,
confirmed_by)` and never touches `list_active`/`run_due_sessions`/scheduler `run_now`. **Gap:** running only
one side produces *unfair* comparison data (baseline and challenger accrue signals at different human
moments). We want both sides evaluated under the **same** explicit action.

## 1. Pair operation need (answers)

- **Why single-session is insufficient:** baseline and challenger must be sampled at the *same* market moment
  to compare fairly; running them at different times mixes different candles/market conditions into the
  comparison and biases the deltas.
- **Order — baseline first, then challenger:** deterministic and intuitive (baseline is the reference). Both
  sides read near-identical recent candles within one request, minimizing skew.
- **Stop if baseline fails/skips?** Distinguish two cases:
  - **Validation failure (422)** on *either* side → reject the **whole** pair *before* evaluating either side
    (no partial execution). Validate both fully up front.
  - **Runtime skip** (dedupe / stale market / no strategy signal) on baseline → **continue** to challenger.
    A skip is a normal outcome, not a failure; aborting would itself create asymmetry.
- **Continue if one side skips (dup/stale/no-signal)?** **Yes** — evaluate both; report each independently.
- **Partial success representation:** the response carries independent `baseline{signal_created,reason,...}`
  and `challenger{...}` sub-objects. "Partial" = one created, one skipped — surfaced plainly, not an error.
- **Same symbol required?** **Yes** — reject (422) on `symbol_code` mismatch. M2.1 *warns* on mismatch, but
  an explicit pair run-once should enforce a fair same-symbol comparison.
- **Same horizon/time bucket required?** **No** at run time — horizon is a *comparison/outcome* parameter
  applied later by M2.1 `compare`, not by signal generation. Run-once takes no horizon.
- **`challenger.baseline_session_id == baseline_id`?** **Yes** — require it (422 on mismatch) so the pair is
  the intended baseline↔challenger relationship, not an arbitrary pairing.
- **Both active?** **Yes.** **Prepared challenger → 422** (UI: "active 전환 후 가능"). Stopped → 422.

## 2. Safety analysis

- **Reuse M2.8 `run_once` twice safely?** Yes — the per-session evaluation core (DRAFT + auto_trade-off +
  registered strategy + symbol gates → `SignalService.generate_and_log_signal` → counters only) is exactly
  what a pair needs, applied to two explicit ids. **No accidental global execution:** the pair never calls
  `list_active`/`run_due_sessions`/`run_now`; it processes only the two provided ids.
- **Touches scheduler/job settings?** No. **Touches Trade/Order paths?** No — same as M2.8 (market-data-only
  `SignalService`, no `TradeService`/`OrderService`/`broker.place_order`).
- **Can it create > 2 SignalLogs?** No — at most one per session (dedupe `exists_for_candle` keeps each at
  0/1), and exactly two sessions are processed → **≤ 2** total.
- **One side stale/missing market data?** That side returns `signal_created=false` with a reason (skipped),
  not a crash; the other side still runs.
- **One side unsupported strategy?** Validation gate → 422 for that side *before* execution (the whole pair
  is rejected up front, since unsupported strategy is a config error, not a runtime skip).
- **Same symbol but different strategy params?** Allowed and expected — that *is* the comparison (baseline
  params vs challenger params on the same symbol). Each side uses its own version's params.

## 3. Option comparison

| Criterion | **A. Frontend-only (call M2.8 twice + M2.1)** | **B. Backend pair endpoint** | **C. Backend pair service, UI later** | **D. Do nothing (single only)** |
|---|---|---|---|---|
| Safety | ⚠️ Med — relationship/symbol validation lives in UI; client could pair mismatched sessions | ✅ High — server enforces baseline_session_id/symbol/active/DRAFT before either runs | ✅ High (same as B) | ✅✅ Highest (no new path) |
| Implementation size | Small (no backend) | Medium | Medium (no UI yet) | None |
| UX clarity | Med (two calls, client orchestrates) | ✅ High (one action, structured result) | n/a until UI | Poor (unfair-comparison risk) |
| Partial-failure handling | ⚠️ In client (fragile) | ✅ Structured, server-side | ✅ Structured | n/a |
| Testability | Low (UI logic) | ✅ High (one service) | ✅ High | n/a |
| Creates SignalLog | ≤2 (two M2.8 calls) | ≤2 | ≤2 | 0 |
| Enables scheduler/job | No | No | No | No |
| Orders/trades reachable | No | No | No | No |
| Rollback/cleanup | Per-call (no txn) | Stop = don't run again | Same | n/a |

**Why A is weaker:** it can fire M2.8 on a baseline/challenger that don't actually correspond (no server check
that `challenger.baseline_session_id==baseline_id` or symbols match), and partial-failure UX is client-coded.
**Why D is rejected:** keeps the unfair-comparison risk that motivated this task.

## 4. Recommended next increment — **Option B (backend pair run-once endpoint)**

A **human-gated** endpoint that validates the baseline↔challenger relationship, then evaluates **exactly the
two** provided active sessions once each (reusing the M2.8 per-session core), returning a structured pair
result. No recurring runner, no global execution, no order/trade. (If the UI proves too large, fall back to
**Option C** — ship backend+tests first, UI later.)

Validation (reject whole pair with 422/404 *before* evaluating either side):
- `confirmed==true` + `confirmed_by` (else 422); baseline exists + challenger exists (else 404);
- both `status=="active"` (else 422; prepared/stopped rejected);
- `challenger.source_type=="signal_challenger"` and `challenger.baseline_session_id==baseline_id` (else 422);
- `baseline.symbol_code == challenger.symbol_code` (else 422);
- each side: `strategy_version_id` present + version exists + **DRAFT** + `auto_trade_enabled` falsy +
  registered `strategy_type` + symbol present (else 422);
- `KIS_REAL_TRADING_ENABLED==false` and `paper_signal_session_runner_enabled==false` (else 422, V1).

Execution: baseline core-evaluate, then challenger core-evaluate (skip is a normal outcome, not abort).
Never call `list_active`/`run_due_sessions`/`run_now`. Update only the two sessions' counters; mutate no
status. **Transaction note:** prefer evaluating both within one request; if reusing M2.8 `run_once` verbatim
(which commits per call), document that the two are committed sequentially (acceptable: each is independently
safe and idempotent via dedupe). A cleaner V1 factors the per-session core out of `run_once` so the pair
commits once.

## 5. Proposed API/UI

**API** — `POST /api/v1/paper-signal-sessions/{baseline_id}/compare/{challenger_id}/run-once-pair`, body
`{ confirmed, confirmed_by }`:
```
{
  "baseline":   { "session_id": …, "signal_created": bool, "signal_id": null|int, "reason": null|str },
  "challenger": { "session_id": …, "signal_created": bool, "signal_id": null|int, "reason": null|str },
  "orders_created": 0,
  "trades_created": 0,
  "runner_enabled": false,
  "comparison_ready_hint": bool,
  "warnings": [
    "This pair run creates SignalLogs only.",
    "No orders or trades are created.",
    "Recurring runner remains disabled."
  ]
}
```
404 unknown baseline/challenger; 422 on any validation gate. Reuses M2.1 `compare` (unchanged) afterward.

**UI** — in the M2.6 comparison block (only when challenger is **active** and baseline available):
- checkbox: **"기준 세션과 challenger 세션을 각각 1회 신호 기록합니다. 주문/거래는 생성하지 않습니다."**
- button: **"페어 신호 1회 기록"**
- result: baseline created/skipped, challenger created/skipped, orders 0, trades 0, "다시 비교" button.
- prepared challenger → "active 전환 후 가능".
Labels: "페어 신호 1회 기록" · "기준/챌린저 각각 1회" · "SignalLog만" · "주문 없음" · "거래 없음" ·
"자동매매 아님" · "반복 실행 아님".
**Forbidden labels:** 자동매매 시작 / 주문 실행 / 실전 연결 / 매매 시작 / 거래 시작 / runner 시작 /
잡 활성화 / 전략 적용 / 자동 적용 / AI가 전략 수정 / 실험 시작. Negative disclaimers only.

## 6. Test plan (for eventual implementation)

- confirmed=false → 422; missing confirmed_by → 422; unknown baseline → 404; unknown challenger → 404.
- baseline not active → 422; challenger not active (prepared/stopped) → 422.
- challenger not `signal_challenger` → 422; `challenger.baseline_session_id != baseline_id` → 422;
  symbol mismatch → 422.
- missing version / version not DRAFT / `auto_trade_enabled=true` → 422 (either side);
  `KIS_REAL_TRADING_ENABLED=true` → 422; `paper_signal_session_runner_enabled=true` → 422.
- baseline duplicate candle → baseline skipped; challenger duplicate candle → challenger skipped;
  stale/missing market data → skipped (not crash); partial success represented (one created, one skipped).
- success creates **at most two** SignalLogs; each references the correct session; **no other active session
  evaluated**; **no `list_active`/`run_due_sessions`/`run_now` call**.
- **no** Trade/Order/AssignmentLog/Experiment/ScannerRuleVersion/StrategyVersion created; **no**
  StrategyVersion/Proposal/session **status** mutation; counters update only for the two selected sessions.
- M2.1 `compare` reflects the pair results; M2.8 single-session run-once still works; `npm run build`.

## 7. Safety proof

- **Not recurring automation:** one explicit, confirm-gated request evaluates the two named sessions once;
  nothing schedules or repeats; `paper_signal_session_runner_enabled` stays false.
- **Cannot run all sessions:** it processes only `baseline_id` and `challenger_id`; it never calls
  `list_active`/`run_due_sessions`/scheduler `run_now`.
- **Cannot place orders:** reuses the M2.8 market-data-only `SignalService` path; no `TradeService`/
  `OrderService`/`broker.place_order`; orders also require ACTIVE/TESTING + `auto_trade_enabled=true` +
  account + `KIS_REAL_TRADING_ENABLED=true` — none of which exist (versions DRAFT, auto_trade false, real
  trading false).
- **≤ 2 SignalLogs:** exactly two sessions, dedupe keeps each at 0/1.
- **Improves fairness:** both sides sampled in one request at the same market moment, on the same symbol,
  with the enforced baseline↔challenger relationship.
- **Recurring scheduler stays a later, separate approval** (Option C of M2.7 / D-22); order/trade paths
  remain out of scope.

## 8. Deferred items

Recurring runner enablement (M2.7 Option C); batch over many pairs/sessions; any order/trade/auto-trade path;
promotion to TESTING/ACTIVE. All remain human-gated and out of M2.9's V1.

## 9. Recommendation

Implement **Option B** (backend pair run-once endpoint) as the safest fair-comparison increment — server
enforces the relationship and runs only the two named sessions once each — falling back to **Option C**
(backend+tests first) if the UI is too large. Keep the recurring runner disabled; do not run either session
as part of this design task.
