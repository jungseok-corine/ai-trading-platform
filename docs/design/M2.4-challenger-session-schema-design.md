# M2.4 Design — Challenger Session Workflow Schema Design

> **Status:** schema design only (no code). Produced during a guarded session at HEAD `7435f12`.
> **Scope boundary:** this document designs the *smallest safe schema change* that will later enable a
> human-gated challenger-session workflow. It implements nothing — no migration, no Alembic file, no model
> edit, no API/frontend edit, no session creation, no readiness/start, no scheduler, no trading. The
> migration itself remains **deferred pending explicit human approval** (D-19).

## 1. Current schema limitation

`PaperSignalSession` (table `paper_signal_sessions`) today:

| Column | Nullable | Note |
|---|---|---|
| `candidate_strategy_proposal_id` | **NOT NULL** (FK → `candidate_strategy_proposals`, CASCADE) | the structural blocker |
| `experiment_id` | nullable (FK → experiments, SET NULL) | |
| `strategy_version_id` | nullable (FK → strategy_versions, SET NULL) | runner reads this |
| `candidate_event_id` | nullable | |
| `symbol_code` | NOT NULL | runner reads this |
| `status` | NOT NULL, `String(20)`, default `"active"` | values used today: `active` / `stopped` |
| `started_by`, `started_at`, … | | |

Verified behaviors that constrain the design:

- **Session creation** (`start_session_from_candidate_strategy_proposal`) is keyed on a
  `CandidateStrategyProposal` that is approved + has `experiment_id` + readiness, and resolves the DRAFT
  version **via `ExperimentVariant`**. The created row sets `candidate_strategy_proposal_id` (NOT NULL).
- **The runner** (`run_due_sessions` → `PaperSignalSessionRepository.list_active()`) selects **only
  `status == "active"`** and then uses **only** `strategy_version_id` (must be DRAFT, `auto_trade_enabled`
  off) and `symbol_code`. **It never reads `candidate_strategy_proposal_id`.**
- **Duplicate-active guard** `find_active_for_proposal(candidate_strategy_proposal_id)` is **per candidate
  proposal** → baseline and challenger cannot coexist under one candidate proposal.
- **Outcome / M2.1 comparison** (`PaperSignalOutcomeService.session_outcomes`, `PaperSignalComparisonService`)
  read by `session_id` and use `strategy_version_id` / `symbol_code` / `status` — **not**
  `candidate_strategy_proposal_id`.

The M2.2 challenger is a **DRAFT `StrategyVersion`** linked from a `StrategyProposal`
(`created_version_id`), with **no** candidate proposal / experiment / variant / readiness. (Full analysis:
`docs/design/M2.3-challenger-session-workflow-gap.md`, decision D-19.)

**Key enabling insight:** because the runner, outcome, and comparison paths do **not** depend on
`candidate_strategy_proposal_id`, the minimal change is to (a) allow that column to be NULL, (b) add explicit
source/traceability columns, and (c) introduce a runner-invisible `"prepared"` status. No new session
table and no Experiment are required.

## 2. Design goals

- Allow a **DRAFT challenger** `StrategyVersion` to become a `PaperSignalSession` via a **human-gated
  preparation** step, then a **separate human-gated start**, then **M2.1 comparison** vs a baseline session.
- **Smallest safe change**; additive and backward compatible (existing CandidateStrategyProposal sessions
  keep working unchanged).
- **No Experiment required**, **no TESTING/ACTIVE** version, **no `approve`**, **no job enablement**, **no
  SignalLog at preparation time**, **no Trade/Order**, **no broker/KIS**.
- Clear traceability: source analysis run → source strategy proposal → challenger version → baseline session
  → challenger session.
- A **prepared (non-running)** session state that the runner cannot pick up until an explicit human start.

## 3. Option comparison

Legend: ✅ good · ⚠️ caveat · ❌ blocker.

| Criterion | **A. Extend PaperSignalSession** (nullable candidate FK + source fields + `prepared` status) | **B. Side context/source table** | **C. Workflow orchestration table** | **D. Separate ChallengerPaperSignalSession table** | **E. Force into Candidate/Experiment path** |
|---|---|---|---|---|---|
| Migration complexity | ✅ Low (alter 1 col nullable + 3–4 additive nullable cols + 1 index + backfill `source_type`) | ⚠️ Med (new table) **and still needs A's nullable change** | ⚠️ Med (new table) **and still needs A or D to create the session** | ❌ High (parallel table) | ✅ none, but ❌ semantically broken |
| Backward compatibility | ✅ existing rows unchanged (`source_type` backfilled) | ✅ | ✅ | ⚠️ two session shapes everywhere | ⚠️ pollutes candidate tables |
| Existing sessions keep working | ✅ | ✅ | ✅ | ⚠️ runner/outcome must union two tables | ⚠️ |
| Prepare a non-running session | ✅ `status="prepared"` (runner filters `active`) | ⚠️ needs A too | ⚠️ needs A/D too | ✅ (own status) | ❌ no prepared state |
| Start only after human confirm | ✅ explicit `prepared`→`active` transition | ⚠️ | ⚠️ | ✅ | ⚠️ |
| Compare baseline/challenger (M2.1) | ✅ unchanged — both are `paper_signal_sessions` rows | ✅ | ✅ | ❌ M2.1 compares two ids in **one** table; would need rework | ⚠️ |
| Experiment required? | ✅ No (version read from `strategy_version_id`) | ✅ No | ✅ No | ✅ No | ❌ Yes (must synthesize) |
| StrategyVersion stays DRAFT | ✅ | ✅ | ✅ | ✅ | ✅ (but path tied to TESTING semantics) |
| Runner/order risk | ✅ None (DRAFT + `prepared` invisible; runner ignores candidate FK) | ✅ | ✅ | ⚠️ new table must replicate safety filters | ⚠️ |
| Duplicate-active guard impact | ⚠️ add challenger-specific guard (by version/source proposal) | ⚠️ | ⚠️ | ⚠️ | ❌ conflicts (D-19 #5) |
| Live/paper trading separation | ✅ unchanged (no order path anywhere) | ✅ | ✅ | ⚠️ duplicated invariants | ❌ |
| UI complexity | ✅ Low (reuse session UI + one prepare action) | ⚠️ | ⚠️ | ❌ two session models in UI | ⚠️ |

**Why B is rejected:** a side table does not remove the `candidate_strategy_proposal_id` NOT NULL blocker —
you would still need A's nullable change *plus* an extra table. Strictly heavier than A, no added benefit
for V1.

**Why D is rejected (for V1):** a parallel session table forces the runner, `PaperSignalOutcomeService`, and
especially **M2.1 comparison** (which compares two ids within a single `paper_signal_sessions` table) to
union/branch across two shapes — large surface, high regression risk, exactly the kind of
"broken/partial schema" the project forbids.

**Why E is rejected:** D-19 — synthesizing a `CandidateStrategyProposal` + `Experiment` + readiness for a
challenger that has none muddies semantics, and the per-proposal duplicate-active guard prevents baseline +
challenger from coexisting. Documented and closed.

**C is a later add-on, not the enabler:** an orchestration table (`baseline_session_id`,
`challenger_proposal_id`, `challenger_version_id`, `challenger_session_id`, `status`) gives the richest audit
trail but **cannot itself create a session** — it sits on top of A (or D). Defer to a later phase once A
proves the shape.

## 4. Recommended schema

**Option A — extend `PaperSignalSession` minimally.**

Additive/relaxing changes to `paper_signal_sessions`:

1. `candidate_strategy_proposal_id` → **make nullable** (drop NOT NULL). FK + CASCADE behavior unchanged for
   existing rows.
2. Add `source_type` `String(30)` **NOT NULL default `"candidate_proposal"`** (server_default for backfill).
   Values: `"candidate_proposal"` (existing flow) | `"signal_challenger"` (M2.4 flow).
3. Add `source_strategy_proposal_id` **nullable** FK → `strategy_proposals` (`ondelete=SET NULL`).
4. Add `baseline_session_id` **nullable** self-FK → `paper_signal_sessions.id` (`ondelete=SET NULL`) — the
   baseline this challenger is meant to be compared against (traceability only; not required by the runner).
5. Reuse the existing nullable `strategy_version_id` for the challenger DRAFT version (already present).
6. **`status`** gains a new value **`"prepared"`** (no enum migration — `status` is `String(20)`). State
   machine: `prepared` → (human start) → `active` → (human stop) → `stopped`. The runner's `list_active()`
   filters `status == "active"`, so `prepared` sessions are **never** run.
7. Add index `ix_paper_signal_sessions_source` on `(source_type, status)` and (optional)
   `ix_paper_signal_sessions_challenger_version` on `(strategy_version_id, status)` to back the
   challenger-specific duplicate guard.

Traceability chain (all already reachable): `source_strategy_proposal_id` → `StrategyProposal`
(`ai_analysis_run_id` → analysis run; `created_version_id` → challenger version; `base_version_id` → baseline
version) and `baseline_session_id` → baseline `PaperSignalSession`.

## 5. Proposed migration steps (for the approved implementation phase — NOT done here)

1. `ALTER TABLE paper_signal_sessions ALTER COLUMN candidate_strategy_proposal_id DROP NOT NULL`.
2. `ADD COLUMN source_type VARCHAR(30) NOT NULL DEFAULT 'candidate_proposal'` (backfills existing rows).
3. `ADD COLUMN source_strategy_proposal_id INTEGER NULL REFERENCES strategy_proposals(id) ON DELETE SET NULL`.
4. `ADD COLUMN baseline_session_id INTEGER NULL REFERENCES paper_signal_sessions(id) ON DELETE SET NULL`.
5. `CREATE INDEX ix_paper_signal_sessions_source ON paper_signal_sessions(source_type, status)`
   (+ optional `ix_paper_signal_sessions_challenger_version`).
6. (Optional, post-deploy) drop the `server_default` on `source_type` once rows are backfilled, keeping the
   application-level default — or keep it; harmless.

All steps are **additive or constraint-relaxing**; no data rewrite beyond the `source_type` backfill, no
column drops. Single revision on top of `o1p2q3r4s5t6`.

## 6. Proposed model/API changes (implementation phase)

**Model** (`PaperSignalSession`): `candidate_strategy_proposal_id` → `Mapped[int | None]`; add `source_type`,
`source_strategy_proposal_id`, `baseline_session_id`. `PaperSignalSessionRead` schema: those fields become
optional/added.

**Service** — new `PaperSignalChallengerSessionService` (separate from the candidate-proposal service):
- `prepare_challenger_session(strategy_proposal_id, confirmed, confirmed_by)` — gates: confirmed +
  confirmed_by; proposal is `paper_signal_analysis`; `created_version_id` (challenger) present and **DRAFT**
  with `auto_trade_enabled` off; `base_version_id` present; resolve baseline session by base version (latest
  session whose `strategy_version_id == base_version_id`); challenger-specific duplicate guard
  (no existing `prepared`/`active` challenger session for this `created_version_id`). Creates **one**
  `PaperSignalSession` with `source_type="signal_challenger"`, `candidate_strategy_proposal_id=NULL`,
  `source_strategy_proposal_id=proposal.id`, `strategy_version_id=challenger`, `baseline_session_id`,
  `symbol_code` (from baseline session/version), `status="prepared"`. **No SignalLog, no version/experiment
  change, no job.**
- `start_challenger_session(session_id, confirmed, confirmed_by)` — `prepared`→`active` only, re-asserting
  the version is still DRAFT + `auto_trade_enabled` off. Still runner-eligible **only when the
  default-disabled job is manually enabled**.
- stop reuses the existing `stop_session`.

**API** (additive; existing routes untouched):
- `POST /strategy-proposals/{id}/prepare-challenger-session` → 201 `{challenger_session_id, status:"prepared",
  auto_trade_enabled:false, baseline_session_id}`; 404/422 gates; 409 duplicate.
- `POST /paper-signal-sessions/{id}/start` (challenger-only; rejects candidate sessions or no-op) →
  `prepared`→`active`, confirm-gated.
- M2.1 `GET /paper-signal-sessions/{baseline}/compare/{challenger}` unchanged.

## 7. Proposed UI flow (implementation phase)

In `StrategyProposalReportCard` M2.2 success block (signal-track proposals only):
1. After "Challenger DRAFT 준비 완료", show **"Paper Signal Session 준비"** (confirm-gated:
   "세션을 준비만 하며 시작/주문/자동매매는 하지 않습니다") → calls `prepare-challenger-session` → shows
   `challenger_session_id` + `status: prepared (실행 전)` + baseline session id.
2. A separate **"신호 기록 시작"** action (confirm-gated) transitions `prepared`→`active` — explicitly distinct
   from preparation.
3. Link to the M2.1 comparison panel (baseline vs challenger) once the challenger session exists.

Labels: "DRAFT-only" · "runner 미대상" · "주문 없음" · "세션 시작은 별도 확인" · "자동매매 아님".
**Forbidden labels:** 전략 적용 / 자동 적용 / 자동매매 시작 / 주문 실행 / 실전 연결 / ACTIVE 전환 /
승인하면 즉시 실행 / AI가 전략 수정 / challenger 실행 / 실험 시작.

## 8. Test plan (implementation phase)

- prepare requires confirmed + confirmed_by (422 otherwise); unknown/ineligible proposal → 404/422;
  duplicate challenger session → 409.
- prepared session: `status=="prepared"`, `candidate_strategy_proposal_id IS NULL`,
  `source_type=="signal_challenger"`, `source_strategy_proposal_id` + `baseline_session_id` set,
  `strategy_version_id` = challenger.
- **runner-invisibility**: `PaperSignalSessionRepository.list_active()` excludes a `prepared` session →
  `run_due_sessions` produces **0** SignalLogs for it; no Trade/Order; no version/experiment status change.
- start transition: `prepared`→`active` only with confirm; re-asserts DRAFT + auto_trade off; no order path.
- challenger version stays **DRAFT**; never TESTING/ACTIVE; `StrategyVersionRepository.list_active()` excludes it.
- **backward compatibility**: existing candidate-proposal sessions still create/start/stop/run; `source_type`
  backfilled to `candidate_proposal`; `find_active_for_proposal` still works for them.
- M2.1 compare(baseline, challenger) works once both sessions exist; read-only.
- no scheduler/job enablement anywhere; `paper_signal_session_runner_enabled` stays false.
- migration upgrade/downgrade round-trips; existing rows valid after downgrade (see §9).
- frontend `npm run build`.

## 9. Rollback / downgrade consideration

Downgrade drops the added indexes and columns (`source_type`, `source_strategy_proposal_id`,
`baseline_session_id`) and **re-adds NOT NULL on `candidate_strategy_proposal_id`**. The re-NOT-NULL step is
only safe if **no challenger rows (NULL candidate FK) exist**. Downgrade procedure: first delete/convert any
`source_type='signal_challenger'` rows (they are paper-only, runner-invisible, orderless — safe to remove),
then re-apply NOT NULL. Document this in the migration's `downgrade()`; if challenger rows exist, downgrade
must fail loudly rather than corrupt the constraint. Forward migration is non-destructive (additive +
backfill). PG convention: leave any added enum-like string values in place (status is a plain string, so
nothing to revert there).

## 10. Safety proof

- **No order/trade possible:** no `TradeService`/`OrderService`/broker is introduced; the signal runner still
  constructs none. Orders require a runner-eligible (ACTIVE/TESTING) version + `auto_trade_enabled=true` +
  account — none exist (challenger DRAFT, auto_trade forced false, `KIS_REAL_TRADING_ENABLED=false`).
- **No runner-eligible version:** challenger stays DRAFT; `StrategyVersion.list_active()` is ACTIVE/TESTING.
- **Prepared sessions cannot run:** `PaperSignalSession.list_active()` filters `status=="active"`; a
  `prepared` session is invisible to the runner until an explicit human `start`. Even after start, SignalLogs
  only flow when the **default-disabled** job is manually enabled.
- **No SignalLog at preparation:** preparation only inserts a session row; `run_due_sessions` is the sole
  SignalLog producer and runs only on enabled-job ticks over `active` sessions.
- **Approval stays blocked:** the shared `approve` path (single + bulk) still rejects/isolates
  `paper_signal_analysis` proposals (D-18); this workflow never calls `approve`.
- **No Experiment required / created:** the session reads its version from `strategy_version_id` directly.
- **Backward compatible & isolated:** existing candidate sessions are untouched; the runner ignores
  `candidate_strategy_proposal_id`, so making it nullable changes no runtime selection.
- **Still human-gated:** the migration, the prepare action, the start action, and enabling the job are each
  separate explicit human steps.

## 11. Deferred items

- The migration itself and all code — **deferred pending explicit human migration approval** (D-19).
- Option C orchestration table (`PaperSignalComparisonWorkflow`) for richer audit — later phase, on top of A.
- Any automatic session start, job enablement, promotion to TESTING/ACTIVE, live/paper orders.
- A formal `status` enum (keep `String` for now; revisit only if states multiply).

## 12. Implementation phases (each separately human-approved)

1. **Phase 0 (this doc):** schema design + decision. No code.
2. **Phase 1 (needs migration approval):** additive migration (Option A) + model + `PaperSignalSessionRead`
   fields. Backfill `source_type`. Tests for backward compatibility + downgrade guard.
3. **Phase 2:** `PaperSignalChallengerSessionService.prepare_challenger_session` + API (creates `prepared`
   session only). Read-only/UI helper to surface it.
4. **Phase 3:** `start_challenger_session` (`prepared`→`active`, confirm-gated) + M2.1 comparison wiring in UI.
5. **Phase 4 (optional):** Option C orchestration table for full baseline↔challenger audit.

Each phase keeps the safety invariants in §10; none enables the job or creates any order path.
