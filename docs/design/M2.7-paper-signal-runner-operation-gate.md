# M2.7 Design — Paper Signal Runner Operation Gate

> **Status:** design / planning only (no code). Produced during a guarded session at HEAD `47715f2`.
> **Scope boundary:** this document designs *how* a user should safely generate SignalLogs for active
> sessions so the baseline↔challenger comparison (M2.1/M2.6) becomes meaningful. It implements nothing —
> no runner enablement, no run, no SignalLog, no scheduler change, no order/trade, no migration.

## 0. Where we are

Completed loop: AI analysis → PENDING `StrategyProposal` → DRAFT challenger `StrategyVersion` →
`prepared` `PaperSignalSession` → `active` `PaperSignalSession` → read-only baseline↔challenger comparison UI.
**Gap:** an `active` session is *eligible* for the signal-only runner, but the runner job is disabled, so no
new SignalLogs accrue and the comparison has nothing to compare.

## 1. Current runner behavior (verified in code)

| Question | Reality (verified) |
|---|---|
| What does `run_due_sessions` do? | Loops `PaperSignalSessionRepository.list_active()` (status=="active"). Per session, requires `strategy_version_id` + version **DRAFT** + `auto_trade_enabled` falsy + a registered `strategy_type`; otherwise it **skips** (records `last_error`). For eligible sessions it calls `SignalService.generate_and_log_signal(...)`. |
| Creates only SignalLog, or trades/orders? | **Only SignalLog.** No Trade/Order anywhere in the path. |
| Calls TradeService/OrderService/StrategyRunnerService/broker/KIS/place_order? | **No TradeService/OrderService/StrategyRunnerService/place_order.** The job builds `SignalService` with a `MarketDataService(broker)` used **only to fetch candles (quotes)** — never to place orders. |
| Market data only, or fetches live price? | Fetches **candles** via `MarketDataService.get_recent_candles(...)` (KIS market-data call if not DB-cached). This is a price/quote read, not an order. |
| Mutates `PaperSignalSession.status`? | **No.** It updates operational counters only: `last_run_at`, `last_error`, `run_count`, `signal_count`. |
| Mutates `StrategyVersion.status`? | **No.** It reads the version; never writes version status. |
| Requires version ACTIVE/TESTING? | **No.** It uses `session.strategy_version_id` directly and *requires* DRAFT (skips non-DRAFT). The trade-capable runner (`StrategyVersionRepository.list_active` = ACTIVE/TESTING) never sees these DRAFT versions. |
| Dedupe of SignalLogs? | `SignalLogRepository.exists_for_candle(strategy_version_id, symbol, side, candle_ts)` → if a signal already exists for that (version, symbol, side, candle), returns None (no duplicate). |
| What if a session errors? | Caught per-session (`except Exception`), recorded in `last_error`; the loop continues; the job does not abort. |
| What does the scheduler job do when `paper_signal_session_runner_enabled=false`? | The job is registered with `env_enabled=lambda s: s.paper_signal_session_runner_enabled` (default **False**), so the recurring trigger is **not scheduled** → it never fires on its own. |

**Important existing mechanism:** `POST /api/v1/autonomous-jobs/{job_id}/run` →
`SchedulerControlService.run_now(job_id, app)` calls `job.func(app)` **directly, regardless of the
enabled flag**. So a one-shot run of `paper_signal_session_runner` is *already possible today* — but it runs
`run_due_sessions` over **all** active sessions (candidate_proposal **and** signal_challenger), not a single
chosen session, and it is the generic ops control (not paper-signal-scoped or specifically confirm-gated).

**Market-closed handling:** `generate_and_log_signal` has a **staleness guard** — if the latest candle is
older than `signal_max_candle_staleness_minutes` (market closed/holiday), it returns None (no signal). So the
runner does not fabricate signals when the market is closed.

## 2. Safety risk analysis

- **New risk when the runner runs:** it starts **writing SignalLogs** for active sessions and makes KIS
  **market-data (candle)** calls. That is the entire new surface — *no* order/trade path becomes reachable
  (no TradeService/OrderService/broker order is constructed anywhere in this path).
- **Can it affect normal trading paths?** No. DRAFT versions are invisible to the trade-capable runner
  (`list_active` = ACTIVE/TESTING); this job builds no TradeService; `KIS_REAL_TRADING_ENABLED=false`.
- **Both active candidate and active challenger sessions selected?** Yes — `run_due_sessions`/`list_active`
  select **all** `status=="active"` sessions regardless of `source_type`. With the recurring job or the
  generic `run-now`, an unrelated active candidate session would also generate signals. **For challenger
  testing this is broader than intended** → argues for a **session-scoped** run-once.
- **Too many SignalLogs?** Bounded per run by (number of active sessions) × (at most one signal per
  version/symbol/side/candle, via the dedupe guard). Recurring scheduling multiplies this every interval; a
  one-shot is naturally bounded.
- **Running during market-closed?** Mitigated by the staleness guard (returns None). A run-once during
  closed hours simply yields "skipped/no signal".
- **Mismatched symbols/time windows in comparison?** M2.1 already returns a `symbol_match=false` warning and
  a low-analyzed-count warning; M2.6 surfaces them. Run-once does not change that.
- **Any order/trade path reachable?** **No** — verified end-to-end.

## 3. Option comparison

| Option | Safety | Size | Creates SignalLog | Enables job | Orders/trades reachable | Makes comparison meaningful | UX clarity | Testability | Stop/rollback |
|---|---|---|---|---|---|---|---|---|---|
| **A. Manual one-shot for all active sessions** (`POST /paper-signal-runner/run-once`, or reuse existing `autonomous-jobs/{id}/run`) | ⚠️ Med — runs **all** active sessions | **None new** (already exists via run-now) / Small | Yes (all active) | No | No | Yes (broad) | Med (broad scope confusing) | Med | Stop = don't run again |
| **B. Session-specific run-once** (`POST /paper-signal-sessions/{id}/run-once`) | ✅ High — only the chosen session | Small–Med | Yes (one session) | No | No | Yes (targeted) | ✅ High | ✅ High | Stop = stop session / don't run |
| **C. Enable recurring scheduler from Ops UI** (toggle `paper_signal_session_runner_enabled`) | ❌ Low-ish — recurring background writes | Tiny (toggle exists) | Yes (recurring, all active) | **Yes** | No | Yes | Med | Low (timing) | Stop = disable job |
| **D. Keep disabled; monitoring/docs only** | ✅✅ Highest | Tiny | **No** | No | No | **No** (no new signals) | n/a | n/a | n/a |
| **E. Batch experiment mode** (explicit baseline+challenger pair, run both once) | ✅ High | Large | Yes (the pair) | No | No | ✅ Best (paired) | High | Med | Don't run |

**Notes:**
- **A** is essentially *already available* via the generic `run-now`, but its all-active scope makes it a
  blunt instrument for challenger testing and it isn't paper-signal-confirm-gated.
- **C** is the riskiest acceptable option: recurring, unattended SignalLog writes. It's a later, separately
  approved step — not V1.
- **D** is the status quo; safe but delivers no measurement.
- **E** is the nicest UX for the baseline↔challenger use case but is larger; defer until B proves the shape.

## 4. Recommended next increment — **Option B (session-specific run-once)**

A **human-gated, session-scoped, one-shot** run that creates **at most one** SignalLog evaluation for **one
explicitly chosen active session**, without enabling the recurring scheduler and without touching any
order/trade path.

- Reuses the exact per-session logic already in `run_due_sessions` (DRAFT + auto_trade-off + registered
  strategy_type guards, `generate_and_log_signal`, dedupe, staleness guard) but applied to **one** session.
- Keeps `paper_signal_session_runner_enabled=false`. Does **not** touch scheduler config.
- Returns a per-session run summary so the user can immediately re-run M2.1/M2.6 comparison.
- Order of safety: B first; **C (recurring enablement) only later, separately approved**; E optional after.

## 5. Proposed API/UI (for the approved implementation)

**API** — `POST /api/v1/paper-signal-sessions/{id}/run-once`, body `{ confirmed, confirmed_by }`:
Eligibility (reject otherwise):
- `confirmed==true` + `confirmed_by` present (else 422);
- session exists (else 404); `session.status=="active"` (else 422 — prepared/stopped rejected);
- `strategy_version_id` present + version exists; version **DRAFT**; `auto_trade_enabled` falsy
  (challenger sessions especially); registered `strategy_type`;
- `KIS_REAL_TRADING_ENABLED` must be false (assert; else 422) — defense in depth;
- **no order/trade path is constructed** (build `SignalService` with market-data only, exactly like the job).

Response: `{ session_id, status, signal_created: bool, signal_id?, reason?, warnings, orders_created: 0,
trades_created: 0, run_count, signal_count }`. Dedupe → `signal_created=false` with reason
"duplicate for candle"; stale/closed market → `signal_created=false` reason "stale candle (market closed?)";
no strategy signal → `signal_created=false` reason "no signal this candle".

**UI** — in the M2.6 comparison/challenger panel:
- Button **"신호 1회 기록"** with a confirm checkbox and copy
  **"이 작업은 SignalLog만 생성하며 주문/거래를 만들지 않습니다."**
- Result line: signal created (with id) / skipped (with reason) + a "다시 비교" link to re-run M2.1 compare.
- Labels: "읽기 전용 비교는 그대로 · 주문 없음 · 거래 없음 · 자동매매 아님 · 스케줄러 미활성".

**Forbidden labels (must not appear):** 자동매매 시작 / 주문 실행 / 실전 연결 / 매매 시작 / 거래 시작 /
runner 시작 / 잡 활성화 / 전략 적용 / 자동 적용 / AI가 전략 수정 / ACTIVE 전환 버튼 / 승인하면 즉시 실행.
Negative disclaimers only.

## 6. Test plan (for eventual implementation)

- confirmed=false → 422; missing confirmed_by → 422; unknown session → 404.
- prepared session → 422; stopped session → 422; active session accepted.
- challenger session requires version DRAFT + `auto_trade_enabled=false` (else 422).
- **no Trade / no Order / no StrategyAssignmentLog created**; **no StrategyVersion mutation**; **no
  StrategyProposal mutation**; **no PaperSignalSession.status mutation** (only counters `run_count`/
  `signal_count`/`last_run_at`/`last_error`).
- **no scheduler/job setting mutation** (`paper_signal_session_runner_enabled` unchanged); **no
  broker `place_order`** (assert the path constructs no TradeService/OrderService).
- dedupe: second run-once on the same candle → `signal_created=false`, no new SignalLog row.
- market-data missing/stale → `signal_created=false` with reason, **not** a crash.
- after a successful run-once, the M2.1 compare endpoint reflects the new SignalLog (analyzed/ signal_count).
- runner job remains disabled throughout.

## 7. Safety proof (recommended V1)

- **Cannot place orders:** the run-once builds `SignalService` with a market-data client only (candles); no
  `TradeService`/`OrderService`/`broker.place_order` is constructed or reachable. Orders also require a
  runner-eligible (ACTIVE/TESTING) version + `auto_trade_enabled=true` + an account + `KIS_REAL_TRADING_ENABLED=true`
  — none of which exist (version DRAFT, auto_trade false, real-trading false).
- **Does not enable recurring automation:** it calls the per-session signal logic directly for one session;
  it does **not** flip `paper_signal_session_runner_enabled` or schedule any trigger.
- **Does not mutate lifecycle:** no change to StrategyVersion/Experiment/StrategyProposal/PaperSignalSession
  **status** — only SignalLog creation + the session's operational counters (as the existing job already does).
- **User stays in control:** each run is an explicit, confirm-gated, one-shot action on one chosen session;
  nothing recurs.
- **Safer than enabling the scheduler:** scope is one session and one tick (bounded by the dedupe guard),
  versus recurring background writes over **all** active sessions at every interval.
- **Still requires explicit future approval:** (a) enabling the recurring runner job (Option C),
  (b) any batch/pair experiment mode (Option E), (c) anything that would move a version to TESTING/ACTIVE or
  touch orders.

## 8. Deferred items

Recurring scheduler enablement (Option C); batch baseline+challenger pair mode (Option E); any order/trade or
auto-trade path; promotion to TESTING/ACTIVE. All remain human-gated and out of M2.7's recommended V1.

## 9. Recommendation

Implement **Option B (session-specific `run-once`)** as the smallest safe way to accrue SignalLogs for a
chosen active session and make the M2.1/M2.6 comparison meaningful, keeping the recurring runner disabled.
Treat **Option C (scheduler enablement)** and **Option E (batch pair)** as separate, later, explicitly
approved steps. Do not enable the runner job or run it as part of this design task.
