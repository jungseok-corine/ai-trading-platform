# M2.3 Design — DRAFT Challenger → PaperSignalSession → Comparison: Workflow Gap Analysis

> **Status:** design / gap-analysis only (no code). Produced during a guarded session at HEAD `516860e`.
> **Scope boundary:** this document analyses the *next* step after M2.2. It implements nothing — no
> migration, no session creation, no version/experiment change, no readiness/start, no scheduler, no trading.

## 0. Context (what is already done)

The paper-signal research loop now reaches:

1. Paper Signal AI Analysis Report (succeeded `AiAnalysisRun`, `target_type=paper_signal_session`).
2. **PENDING `StrategyProposal`** from that analysis (M1, `source="paper_signal_analysis"`).
3. **DRAFT-only challenger `StrategyVersion`** from that proposal (M2.2), `auto_trade_enabled=false`,
   linked via `StrategyProposal.created_version_id`, proposal stays **PENDING**.
4. The shared `ProposalService.approve` path (single + bulk) **rejects** `paper_signal_analysis`
   proposals (D-18) — they cannot become TESTING/runner-eligible.
5. **M2.1 read-only comparison** can compare *any two existing* `PaperSignalSession`s
   (`GET /paper-signal-sessions/{baseline}/compare/{challenger}`).

**The open question:** how does a prepared DRAFT challenger version become a `PaperSignalSession` so it can
be compared (M2.1) against a baseline session — safely and human-gated?

## 1. Current session-creation path (verified in code)

The only way to create a `PaperSignalSession` today is
`POST /candidate-strategy-proposals/{id}/paper-signal-sessions` →
`PaperSignalService.start_session_from_candidate_strategy_proposal`, which requires a
**`CandidateStrategyProposal`** (note: a *different* table from `StrategyProposal`) that is:

| Requirement | Verified detail |
|---|---|
| `status == "approved"` | else `ProposalNotApprovedError` |
| `experiment_id` set (prepared paper experiment) | else `NotPreparedError` |
| readiness approved | `suggested_parameters[_READY_AT_KEY]` present, else `NotReadyError` |
| DRAFT version resolved **via experiment variants** | `ExperimentVariantRepository.list_by_experiment(experiment_id)` → each version must be DRAFT + `auto_trade_enabled` off |
| no duplicate active session | `find_active_for_proposal(proposal_id)` — **per candidate proposal** |

The created row sets `candidate_strategy_proposal_id=proposal.id` (**NOT NULL FK**), `experiment_id`,
`strategy_version_id=versions[0].id`, `candidate_event_id`, `symbol_code`, `status="active"`.

**SignalLogs** are produced **only** by `run_due_sessions`, which runs **only** when the
default-disabled `paper_signal_session_runner` job fires. That job constructs **no `TradeService`** →
no orders/trades/broker. Session status is **only `active` / `stopped`** — there is no
"prepared / not-yet-running" state. `StrategyVersionRepository.list_active()` selects ACTIVE/TESTING only,
so a DRAFT version is never picked up by the trade-capable runner.

## 2. The gap (core finding)

The M2.2 challenger is a **DRAFT `StrategyVersion`** linked from a **`StrategyProposal`**
(`created_version_id`). It has **no `CandidateStrategyProposal`, no `Experiment`, no `ExperimentVariant`,
no readiness**. The session machinery is keyed entirely on the candidate-proposal/experiment/readiness chain.

> **⇒ There is no path — manual or automated — to run an M2.2 challenger version as a `PaperSignalSession`
> today.**

Concrete blockers:

1. `PaperSignalSession.candidate_strategy_proposal_id` is **NOT NULL**; the challenger has no candidate proposal.
2. The start path resolves the version **through experiment variants**; the challenger is on no experiment.
3. **No "prepared / non-running" session state** exists (status is only `active`/`stopped`).
4. Reusing the baseline's candidate proposal/experiment **fails**: the duplicate-active guard is
   **per candidate proposal**, so a challenger session cannot coexist with the baseline session under the
   same proposal — which is exactly what comparison needs.

M2.1 comparison itself is **not** a blocker — it accepts any two existing session ids. The sole missing
piece is *creating the challenger session as an independent, human-gated, non-running session*.

## 3. Option comparison

| Option | Bridges the gap? | Migration | Backend behavior change | Risk | Verdict |
|---|---|---|---|---|---|
| **A. Manual, no code** | ❌ No — no API accepts a bare `version_id` to start a session | No | No | n/a | **Not actually possible today** |
| **B. Read-only helper UI** (show challenger id, "다음 단계", copy/link) | ❌ No (UX only) | No | No | None | Safe, but **does not close the loop** |
| **C. `POST /strategy-versions/{id}/prepare-paper-signal-session`** (create non-started session) | ⚠️ Partial | **Likely yes** | Yes | Med | Needs "prepared" status + nullable/challenger linkage → migration |
| **D. `POST …/start-paper-signal-session`** (start directly from version) | ✅ but couples start to a bare version | Likely yes | Yes | **High** | Defer |
| **E. `PaperSignalChallengerWorkflow` entity** (baseline_session / challenger_version / challenger_session) | ✅ richest | **Yes** | Yes | Med–High | Best long-term home; defer |

**Why A/B do not close the loop:** the session model + start API have no entry point for a challenger
version; a label/copy helper points at a flow that cannot consume the id.

**Why C needs a migration:** a "prepared but not running" session has no representation (no status value),
and an independent challenger session needs its own context — `candidate_strategy_proposal_id` is NOT NULL
and the per-proposal duplicate guard blocks reuse of the baseline's. Minimal schema change would be: make
`candidate_strategy_proposal_id` **nullable**, add `source_strategy_proposal_id` /
`source_challenger_version_id` (nullable FKs), and add a `prepared` session status.

## 4. Recommended next increment

**Two-track recommendation:**

- **Now (zero-risk, optional) — Option B (UI-only helper):** in the M2.2 success block of
  `StrategyProposalReportCard`, show `challenger_version_id`, a copy-id control, and static next-step copy
  ("다음 단계: Paper Signal Session 준비 (별도 확인 필요)") + a link to the comparison panel. **No backend,
  no migration, no session/version/job/order effect.** It must explicitly state the bridge is **not yet
  wired**.
- **M2.3-proper (separate, explicitly human-approved — needs a migration decision):** a human-gated
  challenger-session path (Option C scoped, trending to E). Because the session model genuinely cannot host
  an independent, non-running challenger session without a schema change, this task must **STOP and request
  migration approval before any code** (per the project hard-boundary rule on schema changes).

> **No functional bridge is safe to implement in this increment without migration approval.** If movement is
> desired now, take Option B (UI-only). Otherwise M2.3 begins with a migration-approval request.

## 5. Proposed eventual API/UI (for the approved M2.3 bridge)

**API** (after migration approval):
- `POST /strategy-proposals/{id}/prepare-challenger-session` — body `{confirmed, confirmed_by}`. Derives the
  baseline context from `base_version_id`; creates a **challenger `PaperSignalSession`** with
  `source_strategy_proposal_id`, `source_challenger_version_id=created_version_id`,
  `candidate_strategy_proposal_id=NULL`, status **`prepared`** (not `active`). **Does not** start the
  runner, enable the job, create SignalLogs, or change version/experiment status. 201 →
  `{challenger_session_id, status:"prepared", auto_trade_enabled:false}`; 409 if already prepared; 422 on gates.
- Starting the session stays a **separate explicit human action**; comparison reuses the existing
  `GET /paper-signal-sessions/{baseline}/compare/{challenger}`.

**UI** (M2.2 result + comparison panel) — safe labels only:
"Challenger DRAFT 준비 완료" · "다음 단계: Paper Signal Session 준비" · "전략/주문/자동매매 아님" ·
"세션 시작은 별도 확인 필요" · copy challenger version id · link to comparison once a challenger session exists.

**Forbidden labels (must not appear):** 전략 적용 / 자동 적용 / 자동매매 시작 / 주문 실행 / 실전 연결 /
ACTIVE 전환 / 승인하면 즉시 실행 / AI가 전략 수정 / challenger 실행 / 실험 시작. Negative disclaimers only.

## 6. Test plan (for eventual implementation)

- prepare requires `confirmed` + `confirmed_by`; otherwise 422.
- creates a `PaperSignalSession` in **`prepared`** status only (never `active`); **0 SignalLogs** at prepare time.
- challenger version stays **DRAFT**, `auto_trade_enabled=false`; **no** StrategyVersion/Experiment status change.
- **no** Experiment / ScannerRuleVersion / SignalLog / Trade / Order / StrategyAssignmentLog created.
- **no** job enablement; `paper_signal_session_runner_enabled` stays false.
- `list_active()` (ACTIVE/TESTING) excludes the challenger version → trade-capable runner never picks it up.
- the signal runner emits SignalLogs only for sessions **and only when the job is manually enabled**; a
  `prepared` session emits nothing until explicitly started.
- duplicate prepare → 409; baseline + challenger sessions can coexist (independent contexts).
- `compare/{baseline}/{challenger}` works once both sessions exist; read-only.
- frontend `npm run build`.

## 7. Safety proof

- **No order/trade possible:** the bridge and the signal runner construct no `TradeService`/`OrderService`/
  broker; orders require a runner-eligible (ACTIVE/TESTING) version + `auto_trade_enabled=true` + an account —
  none exist (challenger DRAFT, auto_trade forced false, `KIS_REAL_TRADING_ENABLED=false`).
- **No runner-eligible version created:** challenger stays DRAFT; `list_active()` is ACTIVE/TESTING only.
- **Approval stays blocked:** the shared `approve` path (single + bulk) still rejects/isolates
  `paper_signal_analysis` proposals (D-18); the bridge never calls `approve`.
- **User stays in control:** prepare is confirm-gated and creates a non-running (`prepared`) session; starting
  it and enabling the job remain separate explicit human actions.
- **Still needs explicit human approval:** (a) the **migration** for challenger-session linkage,
  (b) starting the challenger session, (c) enabling the `paper_signal_session_runner` job.

## 8. Deferred items (explicitly NOT in M2.3 until approved)

The functional bridge itself (Option C/E) — deferred pending a **migration-approval request**. The
`PaperSignalChallengerWorkflow` entity (Option E). Direct version→start (Option D). Any job enablement,
session auto-start, promotion to TESTING/ACTIVE, live/paper orders. All remain human-gated.

## 9. Recommendation

Document the gap (this doc). If any near-term work is taken, prefer **Option B (UI-only helper)** as a
zero-risk navigation aid that explicitly notes the bridge is not yet wired. Treat the **functional bridge
(Option C/E) as a separate task that must begin by requesting explicit migration approval** — do not
shoehorn the M2.2 challenger into the existing `CandidateStrategyProposal`/`Experiment` path.
