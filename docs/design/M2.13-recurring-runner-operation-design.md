## 0. 진행 체크포인트

**1) 제품 정렬** — 예. 이 시스템은 AI 보조 paper-signal 연구/비교 도구다. 자동매매 아님 · 실거래 아님 ·
주문 실행 아님. 향후 추가될 상시 런너도 **반드시 SignalLog-only**로 남아야 한다(주문/거래 경로 도달 불가).

**2) 완료된 것 (M2.1~M2.12, 평이하게)**

| 단계 | 활성화하는 것 |
|------|---------------|
| M2.1 | baseline↔challenger 신호 성과 **읽기 전용 비교 API**. 세션/버전 무변경. |
| M2.2 | 신호 트랙 제안에서 **DRAFT-only challenger 버전** 준비(승인/TESTING 아님). |
| M2.5 | 스키마(source 컬럼) + **prepared→active** challenger PaperSignalSession 생애주기(상태 플립만). |
| M2.6 | 비교를 카드 UI로 연결(읽기 전용). |
| M2.8 | **선택한 단일 active 세션**에 사람 클릭으로 신호 1회 평가 → ≤1 SignalLog. |
| M2.10 | **명시한 baseline+challenger 페어**를 한 요청에서 각각 1회 평가(공정) → ≤2 SignalLog (백엔드). |
| M2.11 | 페어 run-once 버튼 (프론트). |
| M2.12 | 비교/UX 정리(단계 가이드 · 안전 배지 · 빈/저데이터 안내 · 페어 1차화). |

각 단계는 **사람 게이트 1개**씩 추가하며, 어디서도 runner/주문/거래에 도달하지 않는다.

**3) 수동 run-once → 상시 런너로 갈 때 바뀌는 것**

- 1회 수동 동작이 **반복 자동 동작**이 된다(사람이 매 tick 클릭하지 않는다).
- **SignalLog 누적량**이 빠르게 늘 수 있다.
- 기존 전역 런너를 쓰면 **모든 active 세션**이 선택된다(범위 폭발).
- 스케줄러/잡 컨트롤이 **운영 리스크**가 된다(상태 혼선, run-now 우회).
- UI가 시작/중지/상태를 **명확히** 보여줘야 한다(자동매매로 오해 금지).

**4) 지금 구현 준비됐나?** — **아니오. 설계만.** 권장 다음 증분은 §4. M2.14 구현은 명시 승인 후.

**안전 드리프트 점검 결과**: 없음. 신호 트랙 전체가 일관되게 SignalLog-only이며 주문/거래 경로가 없다.
단, **검증된 운영 리스크 1건**: `SchedulerControlService.run_now`는 enabled 플래그를 보지 않고 `job.func(app)`을
직접 실행한다(아래 §1). 설계는 이 경로를 **사용하지 않는** 것을 핵심 전제로 한다.

플래그를 우회**한다. 이 둘이 상시 운영의 핵심 위험이다.

## 2. 상시 런너가 새로 들이는 리스크

1. **모든 active 세션이 반복 실행** — 전역 런너는 무관한 세션까지 매 interval 평가.
2. **SignalLog 누적량 급증** — 60초 간격 × 세션 수 × 무인 → 빠르게 증가.
3. **baseline/challenger 불균형** — 한쪽 세션만 활성 윈도우가 달라지면 비교가 불공정.
4. **장 마감 구간 반복 skipped/error** — 의미 없는 run_count 증가 · last_error 노이즈.
5. **스케줄러 상태 혼선** — env 플래그 vs override 행 vs run-now 1회 실행이 헷갈림.
6. **run-now 우회** — 위 §1, 플래그 false라도 전체 실행 가능.
7. **자동매매 오해** — "반복 실행"을 자동매매로 읽을 수 있음(라벨 주의 필수).
8. **주문 실행 오해** — 라벨이 부주의하면 주문 암시.
9. **중첩/동시 실행 race** — 같은 페어를 두 경로가 동시에 → 중복/경합(단, dedupe가 0/1 보장).
10. **장시간 잡이 다음 interval과 겹침** — 느린 시세 응답 시 오버랩.
11. **잘못된 전략 설정 → 반복 에러** — unknown strategy_type 등이 매 tick 반복.
12. **비교 통계 왜곡** — 세션별 active 윈도우가 다르면 누적 표본이 비교 가능성을 떨어뜨림.

## 3. 옵션 비교

평가축: 안전 · 구현 규모 · 범위 통제 · SignalLog량 · 비교 공정성 · 사용자 명확성 · 테스트 용이성 ·

### Option A — 전역 스케줄러 계속 비활성, 상시 런너 없음 (현 상태)
- **안전 최상**. 수동 페어 run-once만. 데이터 누적 느림.
- 구현 0 · 범위 통제 N/A · SignalLog 사람 클릭당 ≤2 · 비교 공정(M2.10) · 명확 · 테스트 기존 · 중지 N/A ·
  스케줄러 OFF · 주문 도달 불가 · 마이그레이션 불필요.

### Option B — 페어 스코프 상시 런너 (계획 객체 없이)
- 사용자가 한 페어 선택, interval로 두 세션 기록. 최대 범위 2 세션. 전역보다 안전.
- 다만 **상태 영속**(어디까지 돌렸나/중지 여부)이 필요 → 사실상 Option E로 수렴.

### Option C — 세션 스코프 상시 런너
- 한 active 세션만 interval 기록. 디버그용. **비교엔 불공정**(짝 안 맞음).
- 범위 1 · 공정성 낮음 · 영속 상태 필요.

### Option D — 기존 전역 `paper_signal_session_runner` 활성
- 전체 active 실행. 코드 변경 최소. **범위 리스크 최고**.
- 비교 공정성 통제 불가 · run-now 우회 노출 · **V1으로 부적절, 연기 권장**.

- 명시 baseline/challenger 페어 · interval · `max_runs`(또는 until-time) · 장중 가드 · 수동 중지 ·

## 4. 권장 다음 증분

**기본 선호: 기존 전역 런너를 아직 켜지 않는다(Option D 거부).**

- **지금(M2.13)**: 설계만.
- **나중(M2.14, 명시 승인 시)**: **Option E — 제한된 pair-scoped 반복 실행 계획**만 구현.

좋은 반복 V1이 갖춰야 할 불변식:

- pair-scoped(전역 아님).
- 명시 `baseline_session_id` + `challenger_session_id` 필수.
- `confirmed=true` + `confirmed_by` 필수.
- 두 세션 모두 **active**.
- `challenger.baseline_session_id == baseline_id`.
- 동일 symbol.
- 두 버전 모두 **DRAFT**.
- 두 버전 모두 `auto_trade_enabled=false`.
- `KIS_REAL_TRADING_ENABLED=false`.
- **주문/거래 생성 불가** — TradeService/OrderService/broker 주문 미구성.
- **SignalLog만** 생성.
- `max_runs` 지원(상한 후 자동 종료).
- `interval_seconds` 지원.
- **수동 중지** 지원.
- 현재 상태 노출.
- 같은 페어에 이미 active 계획이 있으면 거부.
- `autonomous-jobs run-now`를 1차 UX로 쓰지 않음.
- 전역 all-active 런너를 V1으로 켜지 않음.

이 불변식들은 M2.8(`validate_session`)/M2.10(`run_pair` 관계 검증)에서 **이미 구현·테스트된 게이트를 재사용**한다
→ 반복 계획은 "검증된 페어 1회 평가"를 시간축으로 반복하는 얇은 디스패처일 뿐이어야 한다.

## 6. 스키마/설계 고려사항

**신규 테이블 필요(제안): `paper_signal_recurring_runs`** — 기존 어떤 테이블도 "사람-게이트 반복 계획 + 진행
상태"를 표현하지 못한다(force-fit 금지 규칙). 마이그레이션은 **사람 승인 후에만**(D-20 계열).

제안 필드:

```
id, status(active/stopped/completed/failed), scope_type('pair'),
baseline_session_id (FK), challenger_session_id (FK),
interval_seconds, max_runs, completed_runs,
last_run_at, next_run_at,
started_by, stopped_by, stopped_at,
created_at, updated_at, last_error
```

핵심 설계 판단:

- **마이그레이션 필요** → M2.14 전에 별도 승인.
- **전역 스케줄러를 직접 쓰지 않는다.** 옵션:
  - (권장) **단일 디스패처 잡** 하나가 `next_run_at <= now`인 active 계획만 골라, 계획당 **검증된 페어 1회
    평가**(M2.10 `validate`+`evaluate` 재사용)를 수행하고 `completed_runs++`, `next_run_at` 재계산.
    플래그/스케줄 폭증 없이 한 곳에서 제어. **APScheduler 잡을 계획마다 만들지 않는다.**
  - 계획별 APScheduler 잡 생성은 잡 수 폭증·정리 부담 → 비권장.
- **오버랩 방지**: 디스패처는 직렬 처리 + 계획별 `last_run_at` 기준 가드(실행 중 재진입 차단).
- **dedupe**: SignalService candle dedupe가 세션당 tick 0/1 보장(추가 작업 불필요).
- **max_runs 자동 종료**: `completed_runs >= max_runs`면 status='completed', next_run_at=NULL.
- **장 마감/stale**: 기존 staleness 가드로 None→skipped. skipped도 `completed_runs`에 셀지(권장: 시도
  횟수로 카운트하되 `signal_count`는 안 늘림) — 설계 결정 필요.
- **에러 가시화**: `last_error`에 기록, 연속 실패 N회면 status='failed'로 멈춤(무한 에러 루프 방지).

## 8. 안전성 증명

- **왜 pair-scoped가 전역보다 안전한가**: 범위가 정확히 2 세션 + `max_runs` 상한 → SignalLog량·표면이
  유한·예측가능. 전역은 전체 active × ∞ tick으로 무한·불특정.
- **왜 SignalLog-only로 남아야 하나**: 주문/거래 경로를 한 번이라도 열면 "연구 도구"가 "자동매매"가 된다.
  TradeService 미구성 + DRAFT + auto_trade off + 실거래 OFF의 4중 게이트로 도달 불가를 유지한다.
- **왜 max_runs/수동 중지가 필수인가**: 무인 백그라운드 쓰기의 종료 조건과 사람 개입점을 보장 → 폭주 방지.
- **왜 스키마/설계 승인 전 구현 금지인가**: 새 테이블 + 무인 디스패처는 운영 데이터·부하에 영향(§10 규칙).
- **왜 전역 런너 활성이 V1이 아닌가**: 범위 폭발 + run-now 플래그 우회. 통제된 계획 객체가 선행돼야 한다.
- **여전히 명시 승인이 필요한 것**: (a) pair-scoped 반복 계획 설계 채택, (b) `paper_signal_recurring_runs`
  마이그레이션, (c) M2.14 구현 범위.
- **자동매매로 변질 방지법**: 디스패처는 검증된 페어 1회 평가만 반복(주문 경로 없음). 라벨은 "반복 SignalLog
  기록"으로 한정. 전역 런너/run-now를 1차 경로로 쓰지 않는다.
