## 1. Current flow summary

`StrategyProposalReportCard` > `ChallengerComparison` 한 카드 안에 신호 기록 동작이 3종 공존한다:

| 동작 | 컴포넌트 | 출처 | 의미 | 결과 |
|------|----------|------|------|------|
| 페어 신호 1회 기록 | `PairRunOnce` | M2.11 | **단발 공정 비교용** (기준+챌린저 각 1회) | ≤2 SignalLog, 계획 누적 없음 |
| 반복 신호 기록 계획 | `RecurringPlanControls` | M2.14C | **계획 누적용** create/activate/tick/stop | tick당 ≤2 SignalLog, `completed_runs` 누적 |
| 단일 세션만 기록 | `SessionRunOnce` | M2.8 | 고급/디버그용 (`<details>` 강등) | ≤1 SignalLog |
| 신호 성과 비교 보기 | `ChallengerComparison` mut | M2.10/12 | 누적 SignalLog의 forward 성과 비교 | 읽기 전용 표 |

계획 상태머신(서비스 기준):
`prepared`(inert, `next_run_at`=NULL) → `active`(`next_run_at`=메타데이터, 아무도 안 읽음) →
`tick_plan_once`(active·`completed_runs<max_runs`일 때 1회, `completed_runs` +1) →
`max_runs` 도달 시 `completed` / 사람이 `stop` 시 `stopped`.

핵심: **`active`는 실행이 아니다.** active 상태만으로는 신호가 0건 생긴다. tick 버튼을 사람이 눌러야만
SignalLog가 생긴다. `next_run_at`은 미래 디스패처용 메타데이터일 뿐 현재 아무 코드도 읽지 않는다.

## 2. Safety invariants — review

전수 충족(코드/테스트로 확인됨, M2.14A~C 누적 1690 backend passed):

- 계획 create → SignalLog 0 (validator `signal_service=None`, 평가 도달 불가). ✅
- activate → SignalLog 0 (동일, `signal_service=None`). ✅
- stop → SignalLog 0. ✅

- 스케줄러/잡 미활성(`paper_signal_session_runner_enabled=false`). ✅
- 디스패처 부재 — `run_due_sessions`/autonomous-jobs run-now/`SchedulerControlService.run_now`/
  `list_active` 실행 경로 미사용. ✅
- 전역 런너 미사용. ✅
- Trade/Order 0 · `broker.place_order` 미호출 · KIS 주문 TR ID 부재. ✅
- `KIS_REAL_TRADING_ENABLED=false` 유지(config.py 기본값). ✅
- 전 동작 사람 게이트(confirm + onClick) · `useEffect`/`setInterval`/`setTimeout`/폴링 없음. ✅

### 약한 지점 / 경계 모호 (안전 위반은 아님, 인지 리스크)

1. **`next_run_at`이 UI에 노출됨.** 라디오 목록·tick 결과에 `next 2026-…`가 보인다. 디스패처가 없는
   현재 이 값은 **죽은 메타데이터**다. 사용자는 "다음 실행 예약됨"으로 오해할 수 있다. → §3/§4에서 다룸.
2. **`active` 라벨.** 도메인상 "실행 후보"지만 일상어로 "켜짐/돌고 있음"으로 읽힐 위험. 카피로 부정하고
   있으나(active는 실행 아님) 라벨 자체가 강하다.
3. **"반복" 단어.** 계획의 의도(반복 tick 누적)는 맞지만, 현재는 사람이 매번 눌러야 하는 **수동 반복**이다.
   "자동 반복"으로 오해 여지.
4. **세 가지 기록 동작 공존.** PairRunOnce / RecurringPlanControls.tick / SessionRunOnce가 한 화면에 있어
   "어느 걸 눌러야 하나" 혼동 가능(중복 아님 — 목적이 다름, §5).

## 3. UX clarity review (백엔드 모르는 사용자 관점)

1. **"반복 신호 기록 계획"의 의미** — 사용자에겐 "신호를 반복해서 쌓는 계획표". 대체로 통하지만 "반복=자동"
   연상이 문제.
2. **"반복"이 자동 실행로 오해될 수 있나** — **예, 약하게.** 현재 카피("아직 자동 실행되지 않으며…")가
   방어하지만, summary 라벨만 보면 자동으로 비칠 수 있다. → 보조 문구 강화 권장.
3. **"active"가 너무 기술적/위험한가** — **약간.** 영어 도메인 토큰을 그대로 노출. 한국어 사용자에겐
   "켜짐"으로 읽힘.
4. **"대기/후보/수동 기록 가능" 라벨로 바꿔야 하나** — **부분 채택 권장(카피 레벨).** status 영문값
   (prepared/active)을 데이터로 유지하되, UI **표시**에 한글 부제를 병기: `active(수동 tick 가능 상태)`,
   `prepared(준비 — 아직 후보 아님)`. 라벨 자체를 바꿔 status 값을 숨기진 않는다(B-2/B-3 호환·디버그성 유지).
5. **체크박스가 너무 많은가** — create/activate/tick/stop 각 1개(총 4, 단 동시 노출은 보통 2개:
   create + 선택계획 1개 액션). 과하진 않음. **유지 권장**(액션별 분리가 안전 의도를 강화).
6. **체크박스가 도움인가 성가심인가** — 안전 도구로서 도움. 다만 문구가 길어 시각적 부담 → 핵심만 굵게.
7. **액션 순서가 시각적으로 명확한가** — 생성 → (목록/선택) → 상태별 액션 → 결과 순서는 논리적.
   단 PairRunOnce와 RecurringPlanControls가 세로로 붙어 있어 "1회 기록"이 두 군데라 헷갈림.
8. **"페어 신호 1회 기록" ↔ "선택 계획 1회 신호 기록" 관계 명확한가** — **불명확.** 둘 다 "1회 기록"이라
   차이(단발 vs 계획 누적)가 라벨만으로는 안 드러남.
9. **pair run-once ↔ recurring tick-once 중복인가** — **기능 중복 아님**(전자: 계획 무관 단발 공정 비교,
   후자: 특정 계획에 `completed_runs` 누적). 단 **표현 중복**이라 라벨 구분 필요.
10. **자동매매로 오해할 경로 있나** — 직접적 경로는 없음(카피·배지가 강하게 부정). 잔여 리스크는
    (a) "반복" 단어, (b) 노출된 `next_run_at`, (c) "active" 라벨 — 모두 카피로 해소 가능.

## 4. Confusing terms / labels & duplicate actions

| 항목 | 현재 | 리스크 | 제안(카피/구조, 코드 미구현) |
|------|------|--------|------------------------------|

| "반복" 단어 | 섹션 제목 | "자동 반복" 오해 | 부제에 "사람이 누를 때마다 1회씩 누적" 명시 |

## 5. Recommended cleanup before dispatcher

옵션 평가:

- **A — 정리 불필요, 디스패처로** → 비권장. §3-2·§3-8·§4 모호점이 남아 안전 경계 오해 가능.
- **B — 소폭 UI 카피 정리** → **권장(핵심).** active 부제, "반복=수동 누적" 명시, `next_run_at` "예약 아님"
   주석, 두 "1회 기록"에 "단발 비교용/계획 누적용" 라벨.
- **C — 소폭 UI 구조 정리** → **권장(보조).** PairRunOnce(단발)와 RecurringPlanControls(계획)를 시각적으로
   분리(소제목/구분선), 계획 목록에 status 한글 부제. 대규모 재배치는 아님.
- **D — 읽기전용 상태 요약 패널 추가** → 선택(후순위). 계획 1~2개 수준에선 현 목록으로 충분.
- **E — 디스패처 보류하고 수동 tick 데이터 먼저 수집** → **동시 권장(정책).** 디스패처는 막아둔 채
   수동 tick으로 실제 누적/skip 거동을 관찰한다.

**결론: B + C(소폭 카피·구조 정리)를 먼저, 그동안 E(디스패처 보류) 유지.** 디스패처 설계는 정리 후
별도 명시 승인 시.
