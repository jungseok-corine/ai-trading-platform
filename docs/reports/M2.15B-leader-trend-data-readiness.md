## 1. Executive summary

**판정: NOT_READY.** 현재 dev DB는 주도주 추세추종 V1을 지원하지 못한다. 핵심 사실(읽기 전용 측정):

- `market_data`에 **일봉이 0개** — 저장된 timeframe은 `1m`(58,739) / `5m`(210,897) **인트라데이만**.
- 데이터 기간 ~**10 거래일**(2026-06-17 ~ 06-29) — 인트라데이를 일봉으로 집계해도 **최대 ~10일** (252일·MA50·
  MA20(20일)에 턱없이 부족).
- KIS 브로커 클라이언트에 **일봉 OHLCV 조회 메서드 없음**(`get_minute_candles`만; `get_daily_executions`는 주문
  체결, OHLCV 아님; `FHKST01010100`은 현재가 스냅샷).
- `market_data`에 **`trading_value`(거래대금) 필드 없음** — 유동성 지표는 volume 근사만 가능.
- 테마 데이터 **비어 있음**(`Theme`=0, `SymbolThemeMembership`=0) → 테마 클러스터는 V2.

→ **스캐너/전략 구현 전에 일봉 수집 인프라가 선행돼야 한다.**

## 7. KIS daily candle / read-only API feasibility

- 현재 클라이언트는 **일봉 OHLCV 엔드포인트 미구현**. KIS 국내주식 일봉은 보통
  `inquire-daily-itemchartprice`(예 `FHKST03010100`) 류로 **신규 read-only 메서드** 추가가 필요(주문 무관).
- 라이브 프로브 **생략**: (a) 주문 무관 read-only라도 자격/네트워크·rate-limit 리스크, (b) M2.14O에서 외부 API
  rate-limit/키 노출 교훈 — 진단 단계에서 라이브 호출은 위험 대비 이득이 낮아 **건너뜀**(코드/DB 검사로 충분).
- 252봉 요청 가능 여부 — 엔드포인트 추가 시 가능(KIS 일봉은 기간/페이지 조회). 수정주가/원주가·거래량 포함은
  엔드포인트 옵션에 따라 다름 → **수집기 설계 시 확정**. 거래대금은 엔드포인트가 주거나 close×volume 근사.
- rate-limit: 110종×252봉을 한 번에 끌면 EGW00201류 초과 위험 → **backoff·배치·캐시 선행 필수**(M2.14O 패턴).
- **결론: 스캐너 구현 전 (1) 일봉 fetch 메서드 + (2) rate-limit 인지 배치 수집 + (3) `market_data`(또는 일봉 전용)
  캐시 적재가 선행돼야 한다.**
