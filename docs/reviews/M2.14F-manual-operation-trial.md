# M2.14F — Manual Operation Trial

> 운영 시연/검토 전용. 새 기능 없음 · 백엔드/프론트 런타임·마이그레이션 변경 없음 · 스케줄러/잡/API 실행
> 엔드포인트/프론트 실행 컨트롤 없음 · 플래그 활성 없음 · Trade/Order/broker/KIS 없음.
> 목표: M2.14B-3d(스케줄러 통합) 결정 전, **현재 수동 흐름이 이해 가능하고 운영상 유용한지** 검증.

---

## 1. Purpose

baseline↔challenger 비교 + 반복 신호 *계획*(prepared→active→수동 tick)을 사람이 직접 굴려보고, 스케줄러
자동화가 **지금 실제로 필요한지** 판단한다. 자동화를 켜기 전에 (a) 멘탈모델 명확성, (b) 데이터 유용성,
(c) 안전 경계를 확인한다.

---

## 2. Trial mode used

**Mode C(정적 워크스루) + 기존 자동화 테스트를 런타임 증거로 사용.**

- 브라우저 세션 없음 → Mode A(라이브 UI) 불가. 영속 dev Postgres/서버 미확인(`pg_isready` unavailable) →
  Mode B(독립 서버 API 트라이얼) 비실용·위험.
- 대신 **실제 운영 API 경로**(create→activate→tick→readiness→dispatch-core)를 검증하는 **기존 end-to-end
  테스트를 실행**해 런타임 거동을 입증했다(실제 Postgres·트랜잭션 롤백·플래그 미활성·broker 미호출).
  플래그를 켜지 않고, 어떤 라이브 주문/거래도 만들지 않았다.
- **명시**: 라이브 수동 UI 클릭 시연은 실행하지 않았다. 런타임 거동은 코드/문서 워크스루 + 자동화 테스트
  증거(60 passed)로 확인했다.

## 5. What worked

- 단계별 사람 게이트(confirm 체크 + onClick)가 일관됨 — 우발 실행 여지 낮음.
- prepared/active/completed/stopped 상태머신이 명확하고, active가 "실행"이 아님을 카피/배지가 반복 강조(D-25).
- tick 결과가 자족적(생성/skip 사유 · completed/max · orders 0/trades 0 · 비교 힌트) — "무엇이 왜 바뀌었나" 이해 가능.
- 읽기 전용 dispatcher status 패널이 "자동 실행 없음"을 **명시적으로 보여줘** 안전 인지를 높임(M2.14B-3e).
- 안전 경계가 코드/테스트로 견고: ≤2 SignalLog/tick, Trade/Order 0, broker 미호출, 플래그 false.

## 7. Data usefulness

1. **수동 tick이 비교에 충분한 데이터를 만드나?** — tick당 ≤2 SignalLog. 의미 있는 baseline vs challenger
   비교에는 **여러 tick(수십 회) 누적**이 필요 — 단발로는 표본 부족.
2. **스케줄러 전 유용한 수동 tick 횟수?** — 페어당 최소 **수십 회(예 20~50)** 정도가 통계적으로 의미 있는
   승률/평균수익 비교의 시작점(max_runs 기본 30과 정합).
3. **자동화 신뢰 전 최소 수집?** — 페어 2~3개 × 각 ~30 tick 정도의 수동 누적으로 skip 패턴(장마감/중복/무신호)·
   에러 거동을 먼저 관찰.
4. **outcome/성과 뷰가 challenger 품질 판단에 충분?** — 비교표(신호 수/분석/승률/평균·최고·최저)는 1차 판단엔
   충분. 단 **표본 작을 때 편향 경고**는 있으나 신뢰구간/표본수 기반 통계 신뢰도는 약함.
5. **결과 뷰에서 빠진 것?** — 페어별 누적 tick 타임라인 · skip 사유 분포 · 표본수 대비 신뢰도 표식.
6. **스케줄러가 지금 필요한가?** — **아직 아님.** 수동 tick으로 충분히 데이터 수집 가능하고, 자동화는 표본을
   빠르게 늘릴 뿐 새 분석 능력을 주지 않는다. 자동화는 "수동으로 검증된 흐름의 가속"이지 전제조건이 아님.

## 9. UI/UX issues (요약)

- **정보 과밀**: dispatcher status 패널 필드 수 多 → 프론트 노출 시 핵심(can_execute/scheduler 없음/due 자동
  실행 안 함)만 강조하고 상세는 접기 권장.
- **비교 카드 집약**: 4종 동작 + status가 한 카드 → 단발(비교) / 계획(누적) / 상태(읽기) 시각 그룹 분리 권장.
- **표본수 신뢰도 표식 부재**: 비교표에 표본수/신뢰도 힌트 추가하면 challenger 판단 신뢰↑(자동화와 무관한 가치).

## 10. Recommendation

**수동 데이터 수집을 더 하면서, 스케줄러(3d) 직전에 소폭 UI/문서 정리.** 3d는 아직 **승인하지 않는다.**

- **3d로 직행하지 않는다** — 수동 tick으로 데이터 수집이 충분히 가능하고(§7), 자동화는 표본 가속일 뿐 분석
  능력을 추가하지 않으며, status 패널/비교 카드의 정보 과밀이 자동화 전 정리 대상이다.
- **다음 권장 순서**: (1) 수동 tick 데이터 수집 지속(페어 2~3개 × ~30 tick 목표) · (2) M2.14G(가칭)
  소폭 UI 정리(dispatcher status 핵심만 강조 + 비교 카드 그룹 분리 + 표본수 힌트) · (3) M2.14 문서 통합
  (M2.13/M2.14D/M2.14B-3 중복) · (4) **그 후에만**, 충분한 수동 데이터 + 정리가 끝나고 사람 명시 승인 시
  M2.14B-3d(런북 §7 스모크·기본 비활성·잡 첫 줄 플래그 검사).
- 트라이얼 판정: 흐름은 **이해 가능하고 안전·유용**하다. 단 자동화의 *필요성*은 아직 입증되지 않았다(있으면
  편하지만 없어도 막히지 않음).

## 후속(M2.14G 완료): UI 마찰 해소

본 트라이얼이 찾은 UI 마찰을 **M2.14G(프론트 명료화, frontend-only)** 로 해소했다 — 실행 능력 추가 없음:

- 비교 카드 집약 → **4개 그룹 시각 분리**(단발 비교 / 계획 누적 / 디스패처 상태(읽기) / 고급·디버그).
- dispatcher status 정보 과밀 → **컴팩트 요약 + 원시 상세 중첩 접기**.
- 단발 vs 계획 tick 혼동 → 제목/helper로 "누적 안 됨" vs "계획 누적" 명확화.
- 표본수/신뢰도 표식 부재 → **참고용 표본 힌트**(기존 카운트만, 새 지표 없음).

스케줄러 통합(M2.14B-3d)은 여전히 별도·미승인. M2.14G는 명료화만 했고 자동화/실행 표면은 0으로 유지.
